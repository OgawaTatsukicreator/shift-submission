# シフト提出・希望確認システム

Google Apps Script と Google スプレッドシートで動く、従業員ログイン付きの月間シフト希望提出・希望確認・PT申請システムです。

従業員はスマートフォン向けのWeb画面から1か月分のシフト希望を提出し、自分が提出した月間希望とPT申請を確認できます。確定シフトの従業員画面表示は現在の対象外です。

店長・エリア管理者がスプレッドシート上で行う調整・確定処理は関連する管理機能として残していますが、確定結果は従業員向けWeb画面には表示しません。

2026年9月19日に現行コードと文書を確認し、スマートフォン操作、月別下書き、締切・入力検証、管理機能認可、パスワード版、操作ID、通信結果確認、エラー秘匿化、確定表の全件読取と置換を実装しました。初回登録コード、署名付き操作意図、完全な中断再開、版付き確定、設定版を伴う接続先切替は未達です。実スプレッドシートとの結合、実デプロイ、共有権限、実機操作は未確認です。

## スプレッドシート構成

1つのスプレッドシートに全データを集約せず、用途別に4種の役割へ分けます。管理単位・エリア・店舗別の目標設定により、同じ役割で複数の物理ファイルを使用できます。現行コードは、指定されたエリア・店舗へ完全一致する有効行を優先し、次に未指定の共通行、最後に同順位の先頭行を使います。確定入力元はこの解決結果と完全一致するファイルだけを開きます。次の表には今回定めた目標構成を含みます。基本列だけの `操作処理状態` は提出ログ用ファイルへ作成します。`確定版管理`、`業務設定`、`システム制御`、`受入バッチ管理`、シート版の `管理者許可リスト`、`初回登録コード`、`操作状態履歴`、`技術エラーログ` は現行コードではまだ作成されません。

| ファイル種別 | 定数 | 主な用途 |
| --- | --- | --- |
| 全体確認用スプレッドシート | `OVERALL_SPREADSHEET_ID` | 確定シフト、確定版管理、変更履歴、全体確認シート |
| DB管理用スプレッドシート | `ADMIN_SPREADSHEET_ID` | 固定の制御台帳、エリア、店舗、従業員、所属店舗、管理対象ファイル、業務設定、システム制御、受入バッチ管理、管理者許可リスト、操作処理状態、操作状態履歴、ID_DB、パスワードサマリ。現行のID_DB反映時だけ同名の変更履歴も作成される |
| エリア確認用スプレッドシート | `AREA_SPREADSHEET_ID` | 店長・エリア管理者が調整するエリア別シート |
| シフト提出状況兼PT提出log確認用スプレッドシート | `SUBMISSION_LOG_SPREADSHEET_ID` | シフト希望、PT申請ログ、ログインアカウント、ログインセッション、基本操作処理状態。目標版では初回登録コード、技術エラーログも配置する |

現行コードでは、確定とPTの `変更履歴` は全体確認用へ保存されますが、`ID_DB` から反映した従業員マスタの変更履歴はDB管理用へ同名シートを暗黙作成して保存されます。目標版は全体確認用を正本とし、移行時に両方の既存行を統合します。

現行コードは `OVERALL_SPREADSHEET_ID`、`AREA_SPREADSHEET_ID`、`SUBMISSION_LOG_SPREADSHEET_ID` について `管理対象ファイル` を優先します。エリアID・店舗IDが渡された場合は完全一致行を優先し、未指定の共通行へフォールバックします。値が渡されない通常の取得は共通行を優先します。目標版、ロールバック互換版、検証版は、固定DBを環境マニフェストから読み、`システム制御.ACTIVE_CONFIG_REVISION` の設定版から管理単位・エリアID・店舗IDごとに他の接続先を解決します。不足時はコード定数へ切り替えず停止します。

| シート名 | 用途 |
| --- | --- |

## GAS連携手順

1. DB管理用、全体確認用、エリア確認用、提出ログ用のスプレッドシートを用意します。
2. 現行コードでは4つのID定数を設定します。DB管理用以外は `管理対象ファイル` を優先し、指定されたエリア・店舗の完全一致行、未指定の共通行、同順位の先頭行の順で解決します。目標版では、現行の各実呼出しを同じ規則で解決し、未指定を `UNSPECIFIED` の独立キーとして設定版1へ保存します。以後は厳密な解決キーを使い、コード定数へフォールバックしません。
3. Apps Script を開き、`Code.gs` の内容を貼り付けて保存します。
4. Apps Script で HTML ファイルを追加し、ファイル名を `GasApp` にします。
5. `GasApp.html` の内容を貼り付けて保存します。
6. 初回だけスクリプト所有者がApps Scriptエディタから `authorizeOnce()` を実行し、必要な権限を承認します。現在の実装は実行者と実効ユーザーの一致を確認し、Script Properties の `SHIFT_SYSTEM_ADMIN_EMAILS` へ所有者メールを登録します。複数管理者を許可する場合は、所有者がこの値へメールアドレスをカンマ区切りで追加します。`初期シート作成`、ID_DB反映、パスワードサマリ再作成、表示再生成、確定反映は毎回この一覧を検証します。目標の版管理された `管理者許可リスト` シートへの移行は未実装です。
7. DB管理用スプレッドシートのマスタ各シートに、エリア・店舗・従業員・所属店舗・管理対象ファイルを入力します。
8. Apps Scriptを[標準Google Cloudプロジェクト](https://developers.google.com/apps-script/guides/cloud-platform-projects)へ関連付けます。そのプロジェクトで[Cloud Logging専用バケット](https://docs.cloud.google.com/logging/docs/buckets)を作成し、保存期間を30日、閲覧IAMをシステム管理者だけに設定します。さらに、対象Apps Scriptのログだけを専用バケットへ送る[ログシンク](https://docs.cloud.google.com/logging/docs/routing/overview)を作成し、テストログが専用バケットで検索できることを確認します。
9. 「デプロイ」から「新しいデプロイ」を選び、種類を「ウェブアプリ」にします。
10. 実行ユーザーは「自分」、アクセスできるユーザーは運用に合わせて設定します。
11. 発行されたウェブアプリURLを従業員へ共有します。

現行コードには運用開始前に解消すべき未達事項があります。少なくとも、初回登録の追加本人確認、署名・工程履歴を含む操作状態管理、確定入力元の設定版・担当エリア権限と版付きスナップショット、設定版を伴う接続先切替が完了するまでは、新しい本番デプロイとして扱わないでください。

## 目標スキーマへの移行

今回追加した列とシートは目標設計であり、現行コードに移行機能はまだありません。改修版を導入するときは、既存シートのヘッダーを直接上書きせず、管理メニューの目標機能 `スキーマ移行（ドライラン）` と `スキーマ移行を実行` を使います。

1. 所有者が準備処理を実行し、全Script Properties、Webアプリ・API実行可能その他の全デプロイ種別・版・ID・URLまたは呼出し識別子・実行ユーザー・アクセス範囲、HEAD、トリガー詳細、直接・グループ・フォルダ・共有ドライブ由来の権限ID・主体・役割・継承元・配置を記録します。現行DB、全有効行、フォールバック、トリガー元、コンテナバインド親、許可済み確定入力元と、`UNSPECIFIED` を含む実呼出しキーを列挙します。全実効編集主体が各自の資格で所有者別トリガー一覧を提出し、本番トリガーが指定システム所有者1名へ統一されていることを確認します。主体を列挙できない、一覧が欠ける、他所有者のトリガーが残る場合は開始しません。
2. 最初の本番変更より前に、移行前HEAD、全Script Properties、指定所有者へ統一済みのトリガー、全既存デプロイ、アクセス範囲、権限を外部保存して再読取します。復旧入口の作成意図、移行ID、nonceハッシュ、準備コードハッシュ、作成前デプロイ集合、排他的変更リースも先に記録してから、版固定の復旧入口追加と所有者限定APIデプロイだけを最初の許可変更とします。復旧入口はProperties・トリガーの列挙と復元、外部復旧台帳の比較更新、ブートストラップ後の基準引継ぎだけを許可します。ID記録前に停止した場合は作成前集合との差分から専用デプロイ候補を無効化します。独立ランナーの読取専用疎通まで確認します。

## ログインと初回登録

- ログインIDには `従業員マスタ` の `従業員ID` を使用します。
- 現行実装では、初めて利用する従業員は `初めての方` から従業員IDを照合し、本人名を確認してからパスワードを登録します。目標仕様では、管理者が対象従業員へ発行する72時間有効の一回限りの登録コードを追加で照合します。コードはハッシュで保存し、5回の不一致でロックします。使用済みコードは新しい登録には使えませんが、使用操作IDが一致する未完了登録の再開には使用できます。
- パスワードは平文では保存せず、従業員ごとのソルトを使ったハッシュとして `ログインアカウント` に保存します。
- パスワードを5回連続で確認できなかった場合は、15分間ログインを停止します。
- ログインセッションの有効期限は12時間です。ブラウザのタブを閉じた場合も、次回は再ログインが必要です。
- 認証が必要な処理では、セッションの期限・有効状態に加え、従業員マスタとログインアカウントが現在も有効で、アカウント状態が `ACTIVE`、発行時パスワード版が現在版と一致することを毎回確認します。管理者が従業員またはアカウントを無効化した後は、既存セッションも次の操作から拒否し、同じ無効化操作で全セッション行を失効させます。後で再有効化しても旧セッションは戻さず、新規ログインを求めます。
- ログイン後の名前は本人に固定されます。エリアと店舗は主所属を初期表示し、ヘルプ勤務などに合わせて変更できます。
- メイン画面の `パスワード変更` から、現在のパスワードを確認したうえで新しいパスワードへ変更できます。現行コードは通常の単一セッション行を新トークンで上書きしますが、全行失効処理とパスワード版がないため、重複セッション行やパスワード保存後から新セッション発行前の中断時に旧セッション失効を保証できません。
- 認証の正データは提出ログ用スプレッドシートに保存し、DB管理用スプレッドシートの `従業員パスワードサマリ` へ従業員IDとハッシュを同期します。現行コードの同期はベストエフォートで、失敗をコンソールへ記録してもパスワード変更自体は成功として返します。
- `setupMasterSheets()` の初回実行時、旧DB管理用ファイルにログインアカウントがあり提出ログ用ファイルにない場合は、重複を避けてコピーします。旧セッションは移行せず再ログインとし、旧シートは安全のため自動削除しません。
- 認証用シートとパスワードサマリの閲覧・編集権限は、システム管理者だけに限定してください。
- セッショントークンは `sessionStorage` だけで扱い、ローカルストレージ、下書き、コンソールログへ保存しない設計とします。現行コードはこの要件へ未対応です。

- `希望提出`: ログイン中の本人名に固定し、月間シフト希望を新規提出または更新する

## 送信・クリア時の確認

`シフト希望を提出` と `入力をクリア` は、押下後すぐには実行されません。最終確認画面を表示し、確定ボタンを押した場合だけ処理を実行します。

- `提出する`: シフト希望を提出する
- `クリアする`: 入力内容と下書きを削除する
- `キャンセル`: 押下前の画面に戻る

## 受付停止

通常シフト希望の受付を停止する場合は、Apps Script 側の `ACCEPTING` を `false` に変更して再デプロイします。

PT申請は通常シフト希望とは別扱いです。前日まで申請できる運用を前提にしています。
現在のバックエンドではPT申請を管理者用の確定データにも自動反映しますが、従業員画面には申請内容だけを表示します。

通常シフトの目標仕様では、対象月の前月15日23時59分59秒を締切とし、`Asia/Tokyo` で判定します。`ACCEPTING=false` は緊急停止として日時より優先します。現行コードは `DEADLINE_DAY` を画面表示に使うだけで、GAS側の締切判定へは使用していません。

PT申請の目標仕様では、勤務日前日の23時59分59秒まで受け付け、画面とGASの両方で `Asia/Tokyo` を使って判定します。

## 目標とするエラー時の動作

次の内容は今回定めた目標仕様であり、現行コードにはまだ実装されていません。

希望提出、PT申請、確定反映、初回登録、パスワード変更、DB管理書込みには操作IDを付けます。従業員マスタ更新の業務キーは従業員IDとし、受付時のデータ版・最終操作IDを固定します。Web書込み前に、サーバーから操作ID、処理種別、業務キー、秘密情報を除く内容ハッシュ、主体、発行日時、24時間の新規受付期限、30日の墓標受付期限、署名鍵版を結び付けた署名付き操作意図を取得します。クライアントが操作IDを作成することはありません。状態行がない新規受付期限切れIDは業務操作として登録せず、既存状態がある同一操作だけを照合して再開します。署名鍵を更新した場合も、旧鍵は最大墓標受付期限と最大配送遅延を過ぎるまで検証専用で保持します。状態変更は、現在行を新状態、次連番、決定的な履歴出力待ちID、秘密を除いた完全な正規化JSON、そのハッシュへ先に更新します。発生元と連番を一意にして履歴へ配信し、待ちを消すまで次の状態変更を禁止します。不可逆な移行分岐は履歴ではなく `システム制御` を正とします。

初回登録とパスワード変更にも操作IDを付けます。初回登録ではクライアントが256ビット以上の回復トークンを作り、`sessionStorage` だけに保持します。アカウントを `PENDING` で作成し、登録コードを使用済みにした後で有効化します。途中停止したアカウントではログインを許可せず、操作IDと回復トークン、または同じ操作で使用した元の登録コードを確認して再開します。パスワード変更は新しいハッシュとパスワード版を同時に保存します。すべての認証RPCでセッションの発行時版と現在版だけでなく、従業員マスタの現在の有効状態、アカウント状態 `ACTIVE`、アカウント有効フラグも照合します。パスワード変更では旧セッション行の一括失効、サマリ同期、新セッション発行を工程別に続けます。新セッションはパスワード変更操作IDから決めたセッションIDと発行操作IDを持ちます。行保存後に応答を失った場合は、再開時に同じ従業員・現在版の全セッションを失効し、同じ行を新しいトークンハッシュへ置換して有効セッションを1件にします。平文トークンは台帳へ保存しません。従業員またはアカウントの無効化では、アカウント無効化、全セッション失効、サマリ無効化を工程別に行い、新セッションは発行しません。途中停止中も現在の無効状態で認証を拒否し、再有効化後は新規ログインを求めます。

書込みRPCの前に、非秘密操作は操作ID・業務キー・ペイロードハッシュ・署名付き操作意図と両期限をローカルストレージへ、秘密操作は操作ID・業務キー・署名付き操作意図・回復トークンなどの最小記録を `sessionStorage` へ保存し、再読取します。保存禁止、容量不足、破損で一致しない場合は送信せず、入力を保持して理由を表示します。端末記録は墓標受付期限と同じ最長30日で、その後は自動送信も墓標予約も行わず状態確認だけを行います。送信後は操作IDで状態を追跡し、PT申請は同じPT申請IDを維持します。

サーバーが記録する保存状態は未保存、部分保存、保存済みの3種類です。未保存は、その状態へ遷移した時点で永続結果がない状態、部分保存は結果または中間結果が残る未完了状態、保存済みは完了時に結果が保存されていた状態です。後続の通常更新だけでは過去の完了・保存済み記録を書き換えません。状態確認時に、結果参照と現在版・最終操作IDを照合して「現在有効」「後続操作で置換済み」「ロールバックで除去済み」を別に返します。過去の保存状態、完了工程、結果IDは操作状態履歴に残します。結果不明は通信断などで応答を確認できない画面側の状態であり、保存状態として記録しません。

| 画面状態 | 利用者への表示と操作 |
| --- | --- |
| 未保存 | 現在の業務結果がない理由を示し、入力の修正・再試行、または巻戻し・置換後の現在値確認を案内する |
| 保存済み | 完了内容と対象月または申請日を表示する。後続更新済みなら、完了当時の結果と現在値を区別する |
| 結果不明 | 成功・失敗を断定せず、操作IDで提出状況を確認する |
| 部分保存 | 現在残る正データまたは中間結果を明示する。`FAILED_RETRYABLE` なら同じ操作IDの本人再開、`FAILED_NEEDS_REPAIR` なら管理者対応を案内する |
| 後続操作で置換済み | 現在値を表示し、古い入力を自動適用せず新しい操作として確認し直す |
| 移行で巻戻し済み | 受入時の保存結果が現在は保存されていないことと管理者の確認先を表示する |

通信タイムアウトの初期値は20秒です。`google.script.run` の処理は画面のタイムアウト後も続くため、自動再送しません。操作IDによる状態確認を1、2、4、8、16、30秒間隔で行い、その後は30秒間隔を繰り返して開始から最大2分まで続けます。遅れて届いた応答は操作IDが現在の操作と一致する場合だけ反映します。入力内容は保存結果が確定するまで画面に保持します。

状態確認は読取専用です。`FAILED_RETRYABLE` は未保存・部分保存のどちらでも同じ操作IDで残りの工程を本人が再開し、`FAILED_NEEDS_REPAIR` は管理者が修復します。結果不明となった同じ入力を新しい操作IDへ切り替えられるのは、元操作が未保存で競合がない場合だけです。完了済みの現在値を確認した後の通常更新は新しい操作IDで開始できます。`NOT_REGISTERED` が30秒続いた場合、端末ハッシュが一致し、署名付き操作意図の新規受付期限内である場合だけ同じIDを再送します。期限切れでは状態確認と手動確認だけを行い、そのIDを業務操作として新規登録しません。ハッシュ欠落・不一致または秘密操作は、旧ID、業務キー、主体、署名付き操作意図が残り墓標受付期限内の場合だけ、拒否記録専用経路で墓標を予約して新しい署名付き操作意図へ進みます。PT申請IDは維持し、必要情報を失った場合または墓標期限後は自動送信しません。期限切れリースは行を変更せず再試行可能として返します。

正データの保存後に表示用シートの再生成だけが失敗した場合、応答は成功のまま部分保存と警告を返し、従業員の提出が保存済みであることを明示します。操作処理状態は再生成が終わるまで非終端のままです。管理者は固定のDB管理用スプレッドシートの `操作処理状態` から修復待ちを確認し、表示用シートだけを再生成します。

利用者向けメッセージには、何が起きたか、保存されたか、次に何をするかを表示します。下書き保存に失敗した場合は、保存済みと断定せず「画面の入力はそのままです。再読み込み前に確認してください」と案内します。内部例外、スプレッドシートID、スタックトレース、パスワード、セッショントークンは利用者へ表示しません。パスワード、ソルト、セッショントークン、提出内容全体はログにも記録せず、秘密情報とファイルIDを除いたスタック要約だけを管理者向け技術エラーログへ保存します。

すべてのRPCの成功・失敗は、30日保持のCloud Logging専用バケットへ構造化ログとして保存し、技術エラーは提出ログ用 `技術エラーログ` にも90日保持します。閲覧はシステム管理者に限定します。提出ログ用ファイルへ書けない場合はCloud Loggingへ記録し、両方のログ出力が失敗しても、元の処理結果と追跡IDを優先して返します。操作処理状態と履歴は初期180日、最短32日とし、新規受付期限・墓標受付期限の遅い方に最大配送遅延24時間と時計ずれ5分を加えた時刻より前には削除しません。

| 優先度 | 未達事項 |
| --- | --- |
