# シフト提出・希望確認システム 要件定義書

現行実装確認日: 2026年9月19日

本書は、従業員向けGASウェブアプリと管理者向けスプレッドシート機能の目標要件を定める。2026年9月19日の確認後、スマートフォン操作、月別下書き、締切・入力検証、管理機能認可、パスワード版、基本操作ID、通信結果確認、エラー秘匿化、提出障害の追跡IDと技術エラーログ、確定表の全件読取と置換、一回限りの初回登録コードを実装した。署名付き操作意図、工程別の完全な中断再開、版付き確定、設定版を伴う接続先切替は未達事項として残る。

## 1. プロジェクト概要

### 1.1 背景

現在のシフト管理では、従業員の希望提出、店長による調整、確定シフトの共有がGoogleスプレッドシート上に寄りがちである。店舗数や従業員数が増えると、1つのファイル内に月別・店舗別・全体確認用のシートが増え、見通しが悪くなる。

また、従業員がスマートフォンで入力しづらい、他人の入力欄を誤って触る、ヘルプ勤務やPT申請を通常シフトと分けて扱いにくい、自分が提出した希望を確認しづらいという課題がある。

### 1.2 目的

Google Apps Script とGoogleスプレッドシートを使い、従業員がスマートフォンから月間シフト希望とPT申請を提出し、自分の提出内容を確認できる仕組みを作る。管理者向けには、エリア別調整と全体確認のスプレッドシート機能を関連機能として維持する。

### 1.3 対象範囲

- シフト希望提出
- シフト希望の再提出
- PT申請
- 本人の提出済み希望とPT申請履歴の確認
- 従業員IDとパスワードによるログイン、初回登録、パスワード変更
- エリア別シートでのシフト調整
- 確定ボタンによる全体反映
- DB管理用スプレッドシートによるエリア、店舗、従業員、所属、ファイルID管理
- 提出ログ、PT申請ログ、確定シフト、変更履歴の保存

### 1.4 対象外

- 給与計算
- 勤怠打刻
- 自動シフト最適化
- LINE、メールなど外部通知連携
- GoogleアカウントによるSSO
- 従業員向けWebアプリでの確定シフト表示
- 確定シフトの公開通知

### 1.5 現行実装の適合性確認

確認対象は、リポジトリ上の現行GAS版である `GasApp.html` と `Code.gs`、要件定義書、設計書、READMEである。`index.html`、`styles.css`、`app.js` は入力・保存・通信を行わない旧版利用停止案内であり、現行GAS版の適合判定には使用しない。

| 対象 | 判定 | 確認結果 |

| マスタ・ファイル分割 | 一部適合 | 4種のファイル役割とDB管理用 `管理対象ファイル` からの読込、`業務設定` による全体・店舗別の店休日を実装済み。指定されたエリア・店舗の完全一致行を優先し、次に未指定の共通行、同順位の先頭行を使う。`setupMasterSheets()` はエリア確認用ファイルにも参照されない同名シートを作成し、接続先を処理ごとに再解決するため切替中の処理を同じファイル群へ固定できない |

| 課題 | 内容 |
| --- | --- |
| シート増加 | 1つのスプレッドシートに全体、店舗、月別シートが増え続ける |
| スマートフォン操作 | 狭い画面でも日別カードが2列のため時刻選択が細く、固定ヘッダーが入力領域を圧迫する |
| 多店舗勤務 | 所属店舗とヘルプ勤務店舗を分けて管理する必要がある |
| 確定反映 | 店長が調整した内容を管理者用の全体確認へ安全に反映したい |

| マスタ更新 | 店舗や従業員の増減をコード変更ではなくスプレッドシート編集で対応したい |

## 3. システム化後の方針

### 3.1 ファイル分割

システムは以下の4種の役割へスプレッドシートを分ける。管理単位・エリア・店舗別の設定により、同じ役割で複数の物理ファイルを使用できる。

| ファイル種別 | 目的 |
| --- | --- |
| 全体確認用スプレッドシート | 確定シフト、確定版管理、変更履歴、全体確認シートを管理する |
| DB管理用スプレッドシート | 固定の制御台帳として、エリア、店舗、従業員、所属店舗、管理対象ファイル、業務設定、システム制御、受入バッチ管理、管理者許可リスト、操作処理状態、操作状態履歴、ID_DB、従業員パスワードサマリを管理する |
| エリア確認用スプレッドシート | 店長・エリア管理者がエリア別シートを編集し、確定作業を行う |
| シフト提出状況兼PT提出log確認用スプレッドシート | 現行はシフト希望、PT申請ログ、ログインアカウント、ログインセッション、基本操作処理状態、初回登録コードを保存する。目標版では技術エラーログも保存する |

現行コードには例外があり、確定・PTの変更履歴は全体確認用へ保存する一方、`ID_DB` から反映した従業員マスタの変更履歴はDB管理用へ同名シートを暗黙作成して保存する。目標構成では全体確認用を変更履歴の正本とし、移行時に両方の既存行を統合する。

### 3.2 マスタ管理

エリア、店舗、従業員、所属店舗、管理対象ファイルはDB管理用スプレッドシートから読み取る。店舗や従業員の増減は、原則としてコードではなくDB管理用スプレッドシートを更新して対応する。従業員マスタはデータ版と最終操作IDを持ち、ID_DB反映の中断再開時に自己書込みと後続更新を識別できるようにする。

### 3.3 名前選択

従業員画面では、ログインした従業員IDに氏名を固定する。エリアと店舗は主所属を初期表示し、ヘルプ勤務に合わせて変更できる。

### 3.4 確定データ

セルの背景色は管理者が見やすくするための表示と、確定判定の補助に使う。最終的な正データは、全体確認用スプレッドシートの `確定シフト` シートに保存する。

確定データは管理者向け機能で使用し、現段階の従業員向けWebアプリからは取得しない。

## 5. 機能要件

### 5.0 ログイン・パスワード管理

- 従業員IDと登録済みパスワードでログインする。
- 初回利用時は従業員マスタの従業員IDと、管理者が当該従業員へ発行した一回限りの登録コードを照合してから、8文字以上72文字以内のパスワードを登録する。
- 登録コードは従業員ID、コードハッシュ、発行日時、有効期限、状態、失敗回数、使用日時、使用操作ID、発行者IDを持ち、初期有効期限は72時間、連続5回の照合失敗でロックする。平文コードは保存しない。
- 登録成功時は、同じ操作IDでアカウントの `PENDING` 保存、コードの使用済み更新、アカウントの `ACTIVE` 化を工程別に記録する。各工程は再実行しても重複せず、途中失敗後に続きから再開できるようにする。再発行時は従来の未使用コードを失効させ、期限切れ・使用済み・失効済み・ロック済みのコードを新しい登録操作には使用できないようにする。
- 初回登録の開始時は、サーバーが操作ID、処理種別、従業員ID、秘密情報を除くペイロードハッシュ、発行日時、24時間の新規受付期限を結び付けた署名付き操作意図を発行する。クライアントが生成するのは256ビット以上の回復トークンだけとし、`sessionStorage` だけに保存する。サーバーは操作意図と回復トークンのハッシュだけを操作処理状態へ保存する。
- 初回登録が途中停止した場合は、操作IDと回復トークン、または同じ操作IDで使用した元の登録コードを再確認して再開できるようにする。アカウントが `PENDING` の間はログインを許可しない。
- ログイン後のメイン画面から、現在のパスワードを確認したうえでパスワードを変更できる。
- パスワードの正データ保存後に当該従業員の既存セッションをすべて失効させ、パスワードサマリ同期後に新セッションを1件発行する。新セッションはパスワード変更操作IDから決定的に作るセッションIDと発行操作IDを持つ。行保存後に応答を失った場合は、再開時に当該従業員・現在パスワード版の全セッションを失効し、同じセッションID行を新しいトークンハッシュへ置換して有効な新セッションを常に1件にする。平文トークンは台帳へ保存しない。途中停止後にセッションが無効な場合は新しいパスワードで再ログインし、同じ操作IDで未完了工程を再開できるようにする。
- ログインセッションには発行時のパスワード版を保存する。認証が必要なすべてのRPCで、セッションの期限・有効フラグ、従業員マスタの現在の有効フラグ、アカウント状態 `ACTIVE`、アカウント有効フラグTRUE、発行時パスワード版と現在版の一致を毎回確認する。従業員またはアカウントを無効化した直後から既存セッションも次のRPCで拒否し、同じ無効化操作の工程で当該従業員の全セッション行を失効させる。後で再有効化しても旧セッションは無効のままとし、新規ログインを求める。パスワード版を更新した時点でも旧版セッションを無効として扱い、一括失効工程の完了を待たない。
- パスワードはソルト付きハッシュとして保存し、平文では保存しない。
- 連続5回のログイン失敗で15分間ロックし、ログインセッションは12時間有効とする。

### 5.1 シフト希望提出

- 従業員はエリア、店舗、対象月を選択でき、名前はログイン中の本人に固定する。
- 対象月は当月から3か月先までを初期値とし、`ACCEPTABLE_MONTHS_AHEAD` で変更できるようにする。
- 1か月分の日別希望をカード型UIで入力できる。320〜599 CSS pxでは日別カードを1列、区分選択を全幅、開始・終了時刻をカード内の2列で表示し、600 CSS px以上では日別カードを2列にする。
- 入力区分は `未入力`、`勤務可能`、`休み希望`、`有給希望`、`PT` とする。
- `勤務可能` は11:00〜20:00、`PT` は07:00〜22:00の範囲で開始時刻、終了時刻を入力できる。
- 開始時刻が終了時刻と同じ、または終了時刻より遅い場合は送信しない。
- GAS側で対象月と各日付が実在し、日付が対象月内にあり、同じ日付が重複せず、入力区分が許可一覧に含まれることを確認する。
- 備考を入力できる。
- `シフト希望を提出` を押した際は最終確認画面を表示し、確定後に送信する。
- 同じ従業員、同じ対象月の提出は更新扱いにする。
- 各送信に操作IDを付与し、同じ操作IDの再送では重複登録しない。完了済みまたは有効なリースで処理中なら既存状態を返し、再試行可能な失敗または期限切れリースは受付時版を確認して完了済み工程の次から再開する。後続の提出が完了済みなら古い操作を適用しない。

### 5.2 入力クリア

- `入力をクリア` を押した際は最終確認画面を表示する。
- `クリアする` を押した場合だけ入力内容と下書きを削除する。
- `キャンセル` を押した場合は押下前の入力状態に戻る。
- クリア直後は、同じ画面セッションで次の入力変更、別の一括操作、提出完了、画面切替のいずれかが行われるまで、直前の内容へ1回戻せるようにする。
- 全日を一括変更する操作で既存入力を上書きする場合は、変更内容と対象件数を事前に表示する。実行後は、次の入力変更、別の一括操作、提出完了、画面切替のいずれかが行われるまで、同じ画面セッションで直前の内容へ1回戻せるようにする。

### 5.3 下書き

- 入力中の内容はブラウザのローカルストレージに保存する。
- 下書きは従業員IDと対象月の組合せで分離し、月を切り替えても他月の下書きを失わない。
- 下書きには日別希望、対象月、選択したエリア・店舗、備考だけを保存し、セッショントークンや認証情報を含めない。
- 下書きにはスキーマ版、最終更新日時、保存期限を持たせる。初期の保存期限は最終更新から30日とし、`DRAFT_RETENTION_DAYS` で変更できるようにする。壊れた下書きや期限切れの下書きを削除する場合は、利用者へ理由を表示する。
- 画面起動時に下書きがあれば復元する。
- 手動の `下書きを復元` ボタンは表示しない。

### 5.4 PT申請

- 従業員はPT勤務日、勤務エリア、勤務店舗、開始時刻、終了時刻、備考を入力できる。
- 開始時刻と終了時刻は07:00〜22:00の範囲とし、開始時刻は終了時刻より前にする。
- PT申請は通常シフト希望とは別ログに保存する。
- 承認不要運用では、PT申請後に自動で確定シフトへ反映する。
- PT申請は、勤務日前日の23時59分59秒まで可能とする。時刻の判定には `Asia/Tokyo` を使用する。
- 画面では申請できない日付を選択不可にし、GAS側でも日付の実在性と前日制限を再検証する。
- PT申請にも操作IDを付与し、通信再試行で同じ申請を重複登録しない。

### 5.5 希望確認

- 従業員は対象月を指定し、自分が提出した月間希望とPT申請履歴を確認できる。
- 月間希望は提出ログ用スプレッドシートの `シフト希望` から取得する。
- PT申請履歴は同じ提出ログ用スプレッドシートの `PT申請` から取得する。
- 取得対象の従業員IDはログインセッションから決定し、画面から別人を指定できないようにする。
- 希望確認では全体確認用スプレッドシートと `確定シフト` を読み取らない。
- データがない場合は、対象月に提出済み希望がないことを表示する。

### 5.6 エリア別調整

- 店長・エリア管理者はエリア確認用スプレッドシートでシフトを調整する。
- セル値で勤務時間、PT、有給、NGなどを表す。
- 背景色で通常勤務、ヘルプ勤務、調整中、休みなどを表す。
- 確定ボタン実行時、GASがセル値と背景色を読み取り、確定シフトへ変換する。
- 緑と青のセルだけを勤務の確定行へ変換する。赤のセルは休み・勤務不可を示し、新しい有効版の確定勤務行には含めない。
- 確定処理は対象月の全週・全役職グループを読み取り、確定対象として色付けされたセルに未解決の氏名、店舗、日付、セル値が1件でもある場合は書き込み前に停止して対象セルを列挙する。
- 確定入力元は、有効な設定版と認証済み担当エリアからGASがサーバー側で解決する。Web呼出しの `sourceSpreadsheetId` を信用せず、指定されても無視または拒否する。スプレッドシートメニューでは `getActiveSpreadsheet().getId()` を許可済み確定入力元の完全一致で照合する。対象月、エリアID、シート名も同じ設定版から導出した対象と一致する場合だけ読み取る。
- 確定色を解除した勤務、勤務店舗を変更した勤務、削除した勤務は、再確定後の有効版に古い確定行を残さない。旧版は非有効データとして保存期限まで保持する。版の切替範囲は対象月、対象エリア、確定元種別 `エリア調整`、確定元IDで限定し、PT自動確定など別の確定元を削除しない。

### 5.7 全体反映

- 確定ボタン実行後、全体確認用スプレッドシートの `確定シフト` を更新する。
- 全体確認用の `全体_YYYY-MM` シートを再生成する。
- エリア確認用の `エリア_エリアID_YYYY-MM` シートを再生成する。
- 変更履歴を保存する。
- 全体確認とエリア確認の再生成では `確定シフト` を優先する。`確定シフトID` は全版を通じて一意とし、エリア確定行は確定版ID＋版内業務キー、PT行はPT申請IDから決定的に生成する。希望と確定の結合および優先判定には対象月、日付、従業員ID、勤務店舗IDを使用し、同じ業務キーの希望データを重複表示しない。
- 店休日などの業務ルールはマスタまたは運用設定で管理し、コード内の曜日固定ルールだけで決定しない。

### 5.8 DB管理

- DB管理用スプレッドシートに、エリア、店舗、従業員、所属店舗、管理対象ファイル、業務設定、システム制御、受入バッチ管理、管理者許可リスト、操作処理状態、操作状態履歴を持つ。
- `ID_DB` で従業員情報を編集できる。
- `ID_DBの変更を反映` メニューで従業員マスタへ反映できる。
- `管理対象ファイル` は設定版ごとに管理単位・エリアID・店舗ID別の接続先を保持し、`システム制御.ACTIVE_CONFIG_REVISION` が示す1版だけを使用する。目標版は固定DBを環境マニフェストから読み、他のIDをコード定数へフォールバックしない。移行中の停止、書込世代、設定版、方向、分岐、公開境界は `システム制御` の単一行だけを正とする。前進受入とロールバック試験は別の `受入バッチ管理` 行と署名付き受入コンテキストを使う。受入コード版へランダムな実行チャネルIDを焼き込み、署名をチャネルID・コードハッシュ・バッチ・世代・主体へ結び付け、全デプロイ一覧でデプロイとの1対1を監査する。クライアント申告デプロイIDを信頼しない。開放は制御行 `OPENING`、バッチ行 `OPEN`、制御行 `OPEN` の順、封鎖は制御行 `SEALING`、排出後のバッチ行 `SEALED`、制御行 `SEALED`、清掃後のバッチ行 `CLEANED`、制御行 `CLOSED`・アクティブID空の順に期待版・ID・方向・世代をCASする。両行が `OPEN` のときだけ受入書込みを許可し、許可組合せ以外、複数の非終端バッチ、ID・世代不一致は修復待ちで停止する。公開コミット後は旧スナップショットへ戻さず同じ移行IDで前進修復する。
- `従業員パスワードサマリ` に従業員ID、パスワードハッシュ、パスワード版、同期操作ID、更新日時、有効フラグを同期する。
- システム管理者は `操作処理状態` の失敗・修復待ちを確認し、未完了処理の再開、表示用シートの再生成、修復完了の記録を行える。

### 6.1 操作性

- 受入試験対象のUIは `GasApp.html` とし、320×568、360×640、375×667、390×844、430×932 CSS pxの縦向き画面、レイアウト境界の599×932、600×932 CSS px、2列の代表幅768×1024 CSS pxで確認する。
- すべてのタップ対象は、実機で7mm四方以上かつ44×44 CSS px以上を必須とする。`シフト希望を提出`、`PTを申請`、確認画面の実行ボタンは主要操作とし、10mm四方以上を目標とする。
- 独立した操作、とくに結果が異なる操作や破壊的操作は、当たり判定の端から端まで8 CSS px以上離す。タブなど一体型の操作グループは、各項目を44×44 CSS px以上にし、明確な境界を表示して当たり判定を重ねない場合に限り、項目間の空きを設けなくてもよい。
- 320〜599 CSS px幅では日別カードを1列で表示し、区分選択を全幅、開始・終了時刻をカード内の2列で表示する。600 CSS px以上では日別カードを2列にする。320 CSS px幅で横スクロールを発生させない。
- ボタン文言、入力区分、選択済み時刻は、標準文字倍率と200%文字倍率の両方で省略、切れ、重なりなく全文を表示する。
- 週は月曜日始まり、日曜日終わりとし、対象月外の日付カードは表示しない。月初・月末は対象月内の日だけを含む部分週として扱う。月間入力は常に1週だけ展開し、初期表示は1日を含む週とする。最初の週では前週、最後の週では次週の操作を無効化する。週を移動しても入力を保持し、入力エラー時は対象週を自動表示して該当項目へ移動する。
- 入力進捗は `未入力` 以外を選んだ日数を入力済み日数、対象月の暦日数を対象日数として `入力済み日数／対象日数` で表示する。進捗は未入力を禁止する完了率ではなく、入力状況を示す情報として扱う。
- 固定上部領域は対象月と入力進捗を、標準文字倍率では1行56 CSS px以内、200%文字倍率では各1行の計2行104 CSS px以内で表示する。提出操作はセーフエリア対応の固定下部領域へ置き、アカウント操作は固定しないメニューへ移す。本文の上余白とフォーカス移動量は固定領域の実測高に8 CSS pxを加え、入力欄やエラー項目を覆わない。
- すべてのボタンはタップ時に押下中であることが分かる表示にする。
- 送信、クリアなど影響が大きい操作は確認画面を挟む。
- 主操作と確認操作のラベルは `提出する`、`クリアする` など結果が分かる具体的な動詞にし、`OK`、`はい`、`確定` だけの表記を使用しない。
- 受付停止中は通常シフトの提出操作を無効化し、入力開始前に理由を表示する。PT申請が可能な場合は別操作であることを明示する。

操作性の判断には、[SHIG 78 タッチ操作する要素の大きさは7mm以上にする](https://www.sociomedia.co.jp/9786)、[SHIG 93 ホットスポットを広げる](https://www.sociomedia.co.jp/9887)、[SHIG 82 モバイルでは包括的より階層的に](https://www.sociomedia.co.jp/9801)、[SHIG 47 デフォルトボタンには具体的な動詞を用いる](https://www.sociomedia.co.jp/9486) を用いる。

### 6.2 保守性

- 店舗・従業員の増減はDB管理用スプレッドシートの編集で対応する。
- コード内に初期従業員リストや店舗リストを固定しない。
- シートとヘッダーはGASが作成し、マスタデータの中身はスプレッドシートを正とする。

### 6.3 安全性

- 通常シフト希望の受付停止は `ACCEPTING` で制御する。
- GAS側でも必須項目と入力内容を検証する。
- 時間範囲と開始・終了の前後関係は、画面とGASの両方で検証する。
- `google.script.run` から呼び出すWeb RPCは、ログインや初回登録など認証不要と明示した入口を除き、すべて従業員セッションを検証する。管理RPCはセッションと役割をサーバー側で確認し、画面上でボタンを非表示にするだけで認可を代用しない。
- スプレッドシートのカスタムメニューから実行する管理処理は、実行中のGoogleアカウントを `管理者許可リスト` と照合する。アカウントを取得できない実行方式では管理処理を拒否し、同じApps Scriptプロジェクトの管理者専用デプロイから共通バックエンドを呼び出す。別プロジェクトから正データへ直接書き込まない。
- パスワード、セッショントークン、認証ヘッダーは、ローカルストレージ、下書き、操作ログ、エラーログへ保存しない。
- 内部例外、スプレッドシートID、スタックトレース、認証情報を利用者向けメッセージへ含めない。
- 認証の正データとパスワードサマリは、システム管理者だけが閲覧・編集できる権限設定にする。
- 確定データは見た目のシートではなく `確定シフト` を正データとする。
- 外部サイトへの埋め込みは許可せず、Webアプリは `XFrameOptionsMode.DEFAULT` を使用する。

### 6.4 可用性

- Google Apps Script とGoogleスプレッドシートの標準稼働に依存する。
- 障害時はスプレッドシート上の保存データを確認できる状態にする。
- 通信タイムアウトの初期値は20秒とし、`CLIENT_TIMEOUT_SECONDS` で変更できるようにする。タイムアウト時は結果不明として入力を保持し、操作IDで提出状況を確認する。結果不明となった同じ入力を新しい操作IDへ切り替えるのは、元操作が `NOT_SAVED` かつ正データ版・最終操作ID・リースに競合がない場合だけ許可する。完了済みの現在値を確認した後の通常更新は現在版を受付時版として開始できる。`FAILED_RETRYABLE` は `NOT_SAVED` と `PARTIAL` のどちらでも同じ操作IDで再開する。
- 表示用シートの再生成に失敗しても正データの保存結果と分離し、利用者には保存済み・反映待ちを表示する。操作処理状態は再生成が完了するまで非終端の部分保存とし、再生成だけを管理者が再実行できるようにする。
- 移行時のバッチ開放は制御行が `CLOSED` かつアクティブID空の場合だけ許可する。通常書込みは停止解除・ゲート閉鎖・バッチなし、受入書込みは停止中・ゲート `OPEN`・受入専用実行チャネル・有効署名・世代・主体・対象集合一致という排他的な経路を使う。RPC名にかかわらず認証カウンタやセッション時刻を含む正データの永続副作用へ適用し、状態照会と受入中の認証確認は値を更新しない。別の拒否記録専用経路は、既存行がなく、サーバー発行の操作意図についてHMAC、主体、操作ID、処理種別、業務キー、ペイロードハッシュ、30日の墓標受付期限が一致する場合だけ、レート・容量制限下で `REJECTED`, `NOT_SAVED`, `受入バッチ所属=FALSE` の操作行と履歴待ちだけを書けるようにする。署名欠落・不正、主体不一致、期限切れは台帳へ墓標を作らず、レート制限したセキュリティログだけへ記録する。封鎖、排出、所属操作の終端・履歴配信、基準ハッシュ一致後にバッチを `CLEANED`、制御行を `CLOSED`、アクティブID空へ戻す。受入面の無効化前に配送済みで、封鎖後または別バッチ中に認可へ到達した条件適合要求だけを、業務データへ触れる前に非所属の終端拒否墓標として保存する。受入面の無効化後に無効化済み受入URLへ届く要求はトランスポート失敗とし、無効化済み受入URLへ自動再送せず一般公開面で状態照会する。次バッチは中立化後だけ開く。

### 6.5 エラーハンドリングとデータ整合性

- クライアント側の検証は誤入力の予防を目的とし、保存可否の最終判定はGAS側で行う。
- GAS側では、対象月と日付の実在性、対象月内の日付であること、日付の重複、許可された入力区分、時刻範囲、備考が500文字以内であること、店舗とエリアの組合せ、本人が選択できる店舗であることを検証する。
- 選択して提出できる店舗は、主所属店舗、または `従業員店舗設定` で有効フラグがTRUEかつ関係区分が `兼務` または `ヘルプ可` の店舗とする。`ヘルプ候補表示` は候補を画面へ表示するためだけに使い、サーバー側の提出認可には使用しない。
- 通常シフトは、対象月の前月15日23時59分59秒を締切とし、`Asia/Tokyo` で判定する。`ACCEPTING=false` は日時に関係なく緊急停止を優先し、`ACCEPTING=true` の場合も締切後は受け付けない。画面とGASの両方で同じ設定を使用する。
- 希望提出、PT申請、確定反映、初回登録、パスワード変更、DB管理書込みには一意な操作IDを付与する。Web書込みはサーバーから、操作ID、処理種別、業務キー、ペイロードハッシュ、主体、サーバー発行日時、24時間の新規受付期限、30日の墓標受付期限、署名鍵版をHMACで結び付けた操作意図トークンを先に取得し、クライアントは操作IDを生成しない。状態行がない要求は署名と新規受付期限を検証し、期限切れIDを業務操作として新規登録しない。状態行がある同一操作は期限後も照合して再開できる。同じ操作IDの再送は重複登録せず、終端状態または有効な処理中リースなら保存状態、読取時に導出した現行性、結果要約または正データIDを含む既存状態を返す。`FAILED_RETRYABLE` または期限切れリースは、認可、受付時業務データ版、最終操作ID、書込世代を検証してリースを再取得し、完了済み工程の次から再開する。認証情報を含まない処理では、同じ操作IDで異なる内容が届いた場合を競合として拒否する。初回登録は `ACCOUNT_PENDING_SAVED` より前なら登録コードと新規パスワードを再検証・再計算でき、同工程以後は保存済みハッシュを使用して再送された新規パスワードを再適用しない。パスワード変更も認証アカウント保存後は再送されたパスワードを再適用しない。現行署名鍵だけで新規発行し、退役鍵はその鍵の最大墓標受付期限に最大配送遅延と時計ずれを加えた時刻まで検証専用で保持する。
- 操作IDは書き込みの冪等性、状態照会、再開に使用し、結果が確定するまで同じ値を維持する。端末の未完了操作記録は最長30日保持し、期限後は自動再送せず状態照会だけを行う。全RPCは呼出しごとに別の追跡IDを発行し、ログと利用者からの問い合わせに使用する。
- 希望提出は従業員ID＋対象月、PT申請は初回送信時に生成したPT申請ID、確定反映は対象月＋対象エリア＋確定元種別＋確定元ID、初回登録、パスワード変更、従業員マスタ更新は従業員IDを業務キーとし、同一業務キーに対して排他制御を行う。ログイン失敗回数の読取・更新・ロック判定も同じ従業員ID単位の短い排他区間で行う。
- 複数シートへ保存する処理は進行状態を記録し、途中失敗後に未完了処理を再開または修復できるようにする。
- 状態照会は読取専用とする。操作処理状態の状態が `PROCESSING` でもリース期限を過ぎていれば `effectiveStatus=FAILED_RETRYABLE` と `leaseExpired=true` を返し、同じ操作IDの再開操作を表示する。本人の `FAILED_RETRYABLE` は保存状態が `NOT_SAVED` または `PARTIAL` のどちらでも、同じ操作IDと同じ内容の書き込み再送または本人用再開RPCがリースを再取得し、残存結果を照合して続行する。`FAILED_NEEDS_REPAIR` の再開と終端化は保存状態にかかわらずシステム管理者だけに許可する。
- 通信結果を確認できない場合は操作IDで照会する。`NOT_REGISTERED` が30秒続いた非秘密操作は、端末ハッシュが一致し、署名付き操作意図の新規受付期限内である場合だけ同じIDで再送する。期限切れでは状態照会と手動確認だけを許可し、そのIDを業務操作として新規登録しない。ハッシュ欠落・不一致または秘密操作では、旧ID、業務キー、主体と署名付き操作意図が端末に残り墓標受付期限内の場合だけ、拒否記録専用経路で `REJECTED`、`NOT_SAVED` 墓標を予約して新しい署名付き操作意図へ進む。PT申請IDは維持し、必要情報を失った場合または墓標期限後は旧要求の終端確認なしに自動送信しない。
- 書き込み開始時に受付時業務データ版と最終操作ID、有効な設定版、受付時書込世代、解決済み接続先IDを操作処理状態へ固定し、再開時も同じ接続先を使用する。後続操作が同じ業務キーを更新済みなら古い非終端操作を `SUPERSEDED` と `NOT_SAVED` で終端し、現在値を確認した新しい操作だけを許可する。完了済みの過去操作は後続更新だけでは書き換えない。別操作が期限切れリースを引き継げるのは、元操作が `NOT_SAVED` で正データが受付時版から変わっていない場合だけとする。正データの最終操作IDが元操作なら同じ操作IDを先に照合・再開し、`PARTIAL` の期限切れ操作は別操作で上書きしない。
- 保存状態は各遷移時点の業務結果から決める。`NOT_SAVED` は未書込み、コミット前に置換された非終端処理、または補償復元済み、`PARTIAL` はこの操作の結果または中間結果が残る未完了状態、`SAVED` は完了遷移時に結果が保存されていた状態とする。後続の正常な更新だけでは過去の `COMPLETED`, `SAVED` を変更せず、状態照会が正データの版・最終操作IDを比較して `CURRENT`, `REPLACED`, `REMOVED_BY_ROLLBACK`, `NOT_APPLICABLE` の現行性と現在値を返す。`ROLLED_BACK` は基準ハッシュへの復元を確認して常に `NOT_SAVED` とし、遷移前の保存状態、完了工程、結果IDは追記専用の `操作状態履歴` へ残す。
- 状態、保存状態、工程、結果参照を変えるときは、操作行または制御行を新状態、次連番、決定的な履歴出力待ちID、秘密を除いた完全な正規化JSON、そのハッシュへ先に更新する。履歴IDは操作なら `OPERATION:{操作ID}:{連番}`、制御なら `CONTROL:{制御版}` とし、発生元と連番を一意にする。待ちを配信・解除するまで次の比較更新を禁止し、不可逆な分岐を履歴から推定しない。
- 小さな正データ更新は、通常または受入の排他的経路、書込世代、受付時業務データ版、リース所有者・世代、一意性の確認、データ変更、工程記録を同じ `ScriptLock` 区間で完了する。大きな確定スナップショットは操作固有の不変な版IDで構築し、各チャンクと公開前に経路・書込世代を再確認し、公開ポインタの比較・切替だけを同じロック区間で行う。
- 全書込みトリガーは方向、公開またはロールバックのコミット状態、停止、受入ゲート、書込世代をデータ変更前に確認する。前進トリガーは `PUBLICATION_COMMITTED`、互換トリガーは `ROLLBACK_COMMITTED` より前に発火しても書き込まない。履歴・移行・清掃・復旧トリガーは許可工程を限定した専用入口とし、業務関数を呼べないようにする。
- 確定反映では、有効設定版と担当エリアから確定入力元ID、対象月、エリアID、シート名をサーバー導出する。メニュー実行元IDも許可済み入力元へ照合し、呼出し側指定IDまたは設定外の組合せは読取前に拒否する。
- 書込みRPCの前に、非秘密操作は操作ID・業務キー・ペイロードハッシュ、秘密操作は操作ID・業務キー・回復トークンなどの最小回復記録を適切な端末領域へ保存して再読取する。一致しない場合は送信せず、入力保持と具体的な理由を表示する。結果確定後にだけ端末記録を削除する。

| 想定エラー | 必須の処理 |
| --- | --- |
| 必須項目、日付、時刻、区分が不正 | 送信前に該当項目へ表示し、GASでも拒否する。正しい入力例を示す |
| 受付停止、締切超過 | 入力開始前に通常シフトの提出を無効化し、理由と次に可能な操作を示す |
| セッション切れ、権限不足 | 画面入力を保持し、下書きの保存状態を確認してからログイン画面へ戻す。管理操作はサーバー側で拒否する |
| オフライン、通信タイムアウト | 入力を保持し、結果不明として提出状況の確認を案内する。確認前に自動再送しない |
| 二重タップ、同じ操作の再送 | 操作IDで同じ処理と判定し、重複行を作らない |
| 同じ従業員・対象月の同時更新 | 排他制御で直列化し、確定した更新日時と結果を返す |
| 実行停止後に処理リースが期限切れ | 読取専用の状態照会で再試行可能と判定し、同じ操作IDの再開を表示する。後続操作の完了有無を再開前に確認する |
| 古い処理の後に同じ業務キーが更新済み | 古い処理を `SUPERSEDED` と未保存で終端し、現在値を表示して新しい操作として再確認させる |
| スプレッドシート未作成、ID誤り、権限不足 | 書込み前なら停止する。途中発生時の保存状態は、その遷移時点の正データ・中間結果・版・ポインタ・最終操作IDを照合して決め、完了済み工程は再開位置に使う。後続更新後の現行性は照会時に別途導出し、追跡IDと復旧手順を示す |
| 正データ保存後の表示シート再生成失敗 | 提出自体は保存済みとして扱い、派生処理を修復待ちにする |
| 多段保存の途中失敗 | 処理段階を記録し、重複なく再開する。自動復旧できない場合は `操作処理状態` 一覧へ修復待ちとして表示する |
| `ROLLBACK_BASELINE_VERIFIED` 後かつ `PUBLICATION_COMMITTED` 前の移行失敗 | `システム制御` の1行比較更新でロールバック方向、分岐世代、停止、書込世代、受入ゲート封鎖を先に確定する。バッチ行を後続で封鎖し、実行排出、逆順復元、別IDのロールバック試験バッチ清掃を行う。旧データ・設定版1、制御行中立化、前進面停止、互換実行面を照合した1行CASでだけ `ROLLBACK_COMMITTED` とする |
| `ROLLBACK_BASELINE_VERIFIED` 前の移行中断 | 復旧マニフェストから元データ、元アプリ、全権限、トリガー、アクセス範囲を戻す。検証デプロイ・トリガー・複製権限も無効化し、`BOOTSTRAP_COMPLETE` を含むScript Propertiesを存在有無まで移行前へ戻す。照合できない場合は利用を再開しない |
| 受入書込みまたはロールバック後の試験書込みを清掃できない | 停止を維持し、試験前の業務キー別スナップショットと基準ハッシュへ一致するまで前進予約面または既存本番ロールバック予約面を閉鎖版から切り替えない |
| バックアップ・Before-image・復元確認複製の権限超過 | 指定所有者と必要最小管理者以外の直接・グループ・親フォルダ・共有ドライブ由来権限、リンク共有を0件にできるまで移行を開始または公開せず、終端時と削除前にも再確認する |
| `PUBLICATION_COMMITTED` 後の公開失敗 | 旧スナップショットへ戻さず復旧マニフェストと公開後の書込みを保持し、同じ移行IDで前進予約面の版番号更新、ID・URL・`access`・`executeAs` の不変確認、権限、停止解除、読取検証を再開する |
| `ROLLBACK_COMMITTED` 後の復旧失敗 | データ復元を繰り返さず、同じ移行IDで既存本番面の版番号更新、移行前から不変のID・URL・`access`・`executeAs`、全権限経路、停止解除、設定版・世代、代表読取の照合を再開し、すべて一致した場合だけ `ROLLBACK_VERIFIED` とする |
| 保存済みJSONや必須列の破損 | 空データや未提出へ置き換えず、対象レコードを読み取り専用で隔離して追跡IDを表示する。管理者はバックアップまたは変更履歴から修復する |
| 下書き・最小回復記録の破損、保存容量不足 | RPC前の最小回復記録を再読取できなければ送信せず、入力を保持して具体的に案内する。送信済みなら操作IDで結果を照会する |
| 想定外の内部エラー | 入力を保持し、内部情報を隠した案内と追跡IDを表示する |

エラー設計の判断には、[SHIG 15 エラーを回避する](https://www.sociomedia.co.jp/9138) と[SHIG 54 フールプルーフよりフェールセーフ](https://www.sociomedia.co.jp/9530) を用いる。

### 6.6 エラー表示と復旧

- エラー表示は、何が起きたか、保存されたか、利用者が次に行う操作を平易な言葉で示す。
- 入力エラーは該当項目の近くへ表示し、最初のエラー項目へフォーカスを移す。
- 保存済み、未保存、結果不明、部分保存を区別して表示する。
- 通信エラーやサーバーエラーの後も入力内容を保持する。
- 復旧不能または管理者対応が必要なエラーには、問い合わせに使える追跡IDを表示する。書き込み結果の照会が必要な場合は操作IDも表示する。
- 完了、失敗、読込中などの状態は、各画面で読み上げ可能な `role="status"` または同等の仕組みを使って通知する。

エラー文言の判断には、[SHIG 55 エラー表示は建設的にする](https://www.sociomedia.co.jp/9535) を用いる。

### 6.7 ログとプライバシー

- すべてのRPCは開始時に追跡IDを生成し、成功・失敗の構造化ログを標準Google CloudプロジェクトのCloud Loggingへ記録する。ログには追跡ID、処理名、結果、エラーコード、所要時間を含め、書き込み処理では操作ID、業務キー、処理段階も含める。
- 従業員IDと入力内容は障害調査に必要な最小限だけを記録し、パスワード、ソルト、セッショントークンを記録しない。
- 失敗と修復待ちの処理を管理者が一覧できるようにし、正データと表示用データの不一致を検出できるようにする。
- Apps Scriptを標準Google Cloudプロジェクトへ関連付け、対象スクリプトのログを専用ログバケットへ送るログシンクを構成する。専用バケットは初期保存期限30日とし、閲覧権限をシステム管理者に限定する。技術エラーは提出ログ用 `技術エラーログ` にも最長90日保存する。提出ログ用ファイルへ書けない場合はCloud Loggingだけへ記録し、両方への記録が失敗しても元の応答を妨げず、生成済みの追跡IDを利用者へ返す。
- 操作処理状態と操作状態履歴の初期保存期限は180日とし、`OPERATION_RETENTION_DAYS` で変更できるが32日未満を拒否する。最大配送遅延は初期24時間、時計ずれは初期5分とする。日次トリガーは `COMPLETED`、`REJECTED`、`SUPERSEDED`、`ROLLED_BACK` の期限超過に加え、新規受付期限と墓標受付期限の遅い方へ最大配送遅延と時計ずれを加えた時刻を経過し、履歴出力待ちが空、現在行の最新履歴連番・ID・JSONハッシュと最終履歴が一致、受入所属なら所属バッチ `CLEANED` をすべて満たす行だけを削除候補にする。`ScriptLock` 内で再読取し、単一のSheets API `spreadsheets.batchUpdate` に現在行と対応履歴の行削除をまとめて原子的に適用する。失敗、不一致、孤児、非終端状態、または不正な保持設定は保持して管理者へ警告する。システム管理者が設定、実行結果、手動削除を管理する。
- 削除済み操作IDの遅延再送も、状態行がない新規受付では署名済み発行期限により拒否する。保持期限の前後で削除と181日目の再送を競合させ、同じIDが新規操作として作られないことを試験する。

### 7.1 業務設定

`業務設定` は設定キー、適用範囲、適用先ID、設定値、有効開始日、有効終了日、有効フラグを持つ。締切、タイムゾーン、店休日などの業務ルールを管理する。停止、書込世代、設定版、移行分岐の表示用写しを置く場合も読取専用とし、処理判断には使わない。

### 7.2 システム制御と受入バッチ管理

`システム制御` は業務制御版、自己列を除外したチェックサム、停止・設定・移行・バッチ・公開状態、完全な履歴待ち本文を持つ。履歴本文の前後投影からチェックサム方式・チェックサム・待ち列・更新日時を除外する。履歴ACKは制御版を増やさず新イベントを作らず、履歴一致確認後に待ちだけを消す。

`受入バッチ管理` は、対象業務キー集合ハッシュ、Before-image方式版、所有者限定の不変マニフェスト参照・版・内容ハッシュを持つ。マニフェストは各キーの元値、版、ポインタ、行なしを保持し、開放前に再読取する。封鎖後は同じ参照だけから復元し、全所属操作の履歴ACKと基準ハッシュ一致後だけ清掃済みとする。遅延要求は非所属墓標にする。

### 7.3 初回登録コード

`初回登録コード` は従業員ID、コードハッシュ、発行日時、有効期限、状態、失敗回数、使用日時、使用操作ID、発行者IDを持つ。状態は発行済み、使用済み、期限切れ、失効済み、ロック済みを区別する。

### 7.4 操作処理状態

`操作処理状態` は固定DBに置き、操作ID、操作発行日時、新規受付期限、墓標受付期限、操作意図鍵版、操作意図トークンハッシュ、処理種別、業務キー、ペイロードハッシュ、回復トークンハッシュ、受付時版、設定版、書込世代、接続先、受入バッチID、受入バッチ所属、状態、保存状態、リース、結果、現在状態の遷移連番、最後に配信済みの最新履歴連番・ID・JSONハッシュ、完全な履歴出力待ちJSONとハッシュを持つ。所属TRUEだけを清掃集合へ含め、非所属墓標と分離する。現行性は結果参照と正データの現在版・最終操作IDから照会時に導出し、列へ固定しない。

### 7.5 操作状態履歴

`操作状態履歴` は固定DBの追記専用台帳である。状態CASで現在行の遷移連番を1増やし、完全な待ち本文をその連番の一意なIDで配信する。ACKは状態と遷移連番を変えず、履歴ID・ハッシュ一致後に最新履歴連番・ID・JSONハッシュへ値を移して待ち列を消去する。ACK完了まで次の遷移を禁止する。

### 7.6 技術エラーログ

`技術エラーログ` は発生日時、追跡ID、操作ID、処理名、処理段階、エラーコード、再試行可否、所要時間、内部要約を持つ。内部要約には秘密情報とスプレッドシートIDを除去したスタック要約を含められる。従業員IDは必要な場合だけ記録し、提出ペイロード全体、パスワード、ソルト、セッショントークンは保存しない。

### 7.7 確定版管理

`確定版管理` は、対象月、対象エリア、確定元種別、確定元IDごとの有効版を示すポインタ行と、構築中・検証済み・有効・旧版・失敗を区別する版行を持つ。版行には版ID、親版ID、行数、内容ハッシュ、操作ID、作成日時を保存し、ポインタ行には有効版IDとポインタ世代を保存する。読取処理はポインタ行の有効版IDを正とする。

## 8. 運用要件

- GASエディタには `Code.gs` と `GasApp.html` を貼り付ける。
- ローカル編集後はGAS側へ手動貼り替えまたは同期ツールで反映する。
- 初回だけApps Scriptエディタから `authorizeOnce()` を実行し、実行者がプロジェクト所有者であることを確認して必要な権限を承認する。その処理で `管理者許可リスト` を作成し、所有者を最初のシステム管理者として登録して `BOOTSTRAP_COMPLETE` を設定する。以後の `初期シート作成` を含む管理メニューは許可リスト照合を必須とする。
- 旧DB管理用ファイルにログインアカウントがある場合、初期シート作成時に提出ログ用ファイルへ重複なしでコピーする。旧セッションは移行せず再ログインとし、旧シートは自動削除しない。
- 必要に応じて `パスワードサマリ再作成` メニューで管理用サマリを再同期する。
- DB管理用スプレッドシートのマスタは、有効フラグで表示・非表示を制御する。
- 不要になった従業員や店舗は削除ではなく有効フラグをFALSEにする。
- 管理者は `操作処理状態` の失敗・修復待ちを確認し、表示用シートの再生成または未完了処理の再開を行う。
- 管理対象シートはDeveloper Metadataの `SHIFT_SYSTEM_SCHEMA_VERSION` にスキーマ版を持つ。通常処理はコードの期待版と一致することを読取前に確認し、不一致の場合はヘッダーを自動上書きせず処理を停止する。初回ブートストラップでは、バックアップ後に旧 `管理対象ファイル` から目標スキーマの一時シートと設定版1を作り、検証後に名前切替とMetadata設定を行う。正式化した `管理対象ファイル` は後段変換から除外し、設定版1を再作成しない。移行IDは操作IDとして `操作処理状態` に保存する。
- 既存環境では全Script Propertiesを保存し、現行の各実呼出しキーを行順規則で解決する。ID未指定呼出しは `UNSPECIFIED` の独立キーとして実効IDを記録する。コンテナ親と許可済み確定入力元も含め、遮断・排出後に物理集合と論理解決表を再計算して確認済みハッシュと照合する。設定版1はこの解決表を明示的に再現する。
