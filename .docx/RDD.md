# シフト提出システム 要件定義書

## 1. プロジェクト概要

### 1.1 背景

現在のシフト管理では、従業員の希望提出、店長による調整、確定シフトの共有がGoogleスプレッドシート上に寄りがちである。店舗数や従業員数が増えると、1つのファイル内に月別・店舗別・全体確認用のシートが増え、見通しが悪くなる。

また、従業員がスマートフォンで入力しづらい、他人の入力欄を誤って触る、ヘルプ勤務やPT申請を通常シフトと分けて扱いにくい、確定シフトを個人別に確認しづらいという課題がある。

### 1.2 目的

Google Apps Script とGoogleスプレッドシートを使い、従業員がスマートフォンから月間シフト希望とPT申請を提出でき、管理者がエリア別に調整し、確定シフトを全体確認用シートと個人画面へ反映できる仕組みを作る。

### 1.3 対象範囲

- シフト希望提出
- シフト希望の再提出
- PT申請
- 希望・確定シフト確認
- エリア別シートでのシフト調整
- 確定ボタンによる全体反映
- DB管理用スプレッドシートによるエリア、店舗、従業員、所属、ファイルID管理
- 提出ログ、PT申請ログ、確定シフト、変更履歴の保存

### 1.4 対象外

- 給与計算
- 勤怠打刻
- 自動シフト最適化
- LINE、メールなど外部通知連携
- Googleアカウントごとの厳密な認証・認可制御

## 2. 現行課題

| 課題 | 内容 |
| --- | --- |
| シート増加 | 1つのスプレッドシートに全体、店舗、月別シートが増え続ける |
| UIの悪化 | 従業員が増えると名前選択欄が長くなり、スマホで選びにくい |
| 多店舗勤務 | 所属店舗とヘルプ勤務店舗を分けて管理する必要がある |
| 確定反映 | 店長が調整した内容を全体と個人画面へ安全に反映したい |
| PT申請 | 通常シフト希望とは別に、前日まで申請できるログが必要 |
| マスタ更新 | 店舗や従業員の増減をコード変更ではなくスプレッドシート編集で対応したい |

## 3. システム化後の方針

### 3.1 ファイル分割

システムは以下の4つのスプレッドシートを使う。

| ファイル種別 | 目的 |
| --- | --- |
| 全体確認用スプレッドシート | 確定シフト、変更履歴、全体確認シートを管理する |
| DB管理用スプレッドシート | エリア、店舗、従業員、所属店舗、管理対象ファイル、ID_DBを管理する |
| エリア確認用スプレッドシート | 店長・エリア管理者がエリア別シートを編集し、確定作業を行う |
| シフト提出状況兼PT提出log確認用スプレッドシート | シフト希望、PT申請ログを保存する |

### 3.2 マスタ管理

エリア、店舗、従業員、所属店舗、管理対象ファイルはDB管理用スプレッドシートから読み取る。店舗や従業員の増減は、原則としてコードではなくDB管理用スプレッドシートを更新して対応する。

### 3.3 名前選択

従業員画面では、エリア選択、店舗選択、名前選択の順番にする。選択した店舗に通常表示する従業員だけを名前候補に表示し、ヘルプ候補者は通常の名前候補に混ぜない。

### 3.4 確定データ

セルの背景色は管理者が見やすくするための表示と、確定判定の補助に使う。最終的な正データは、全体確認用スプレッドシートの `確定シフト` シートに保存する。

## 4. 利用者

| 利用者 | 主な操作 |
| --- | --- |
| 従業員 | シフト希望提出、PT申請、希望・確定確認 |
| 店長 | エリア確認用シートでの調整、確定ボタン実行 |
| エリア管理者 | エリア全体の配置確認、ヘルプ調整、確定反映 |
| システム管理者 | DB管理、全体確認、提出ログ確認、変更履歴確認 |

## 5. 機能要件

### 5.1 シフト希望提出

- 従業員はエリア、店舗、名前、対象月を選択できる。
- 店舗選択後、該当店舗に通常表示する従業員だけを名前候補に表示する。
- 1か月分の日別希望を2列カード型UIで入力できる。
- 入力区分は `未入力`、`勤務可能`、`休み希望`、`有給希望`、`PT` とする。
- `勤務可能` と `PT` は開始時刻、終了時刻を入力できる。
- 備考を入力できる。
- `シフト希望を提出` を押した際は最終確認画面を表示し、確定後に送信する。
- 同じ従業員、同じ対象月の提出は更新扱いにする。

### 5.2 入力クリア

- `入力をクリア` を押した際は最終確認画面を表示する。
- `クリアする` を押した場合だけ入力内容と下書きを削除する。
- `キャンセル` を押した場合は押下前の入力状態に戻る。

### 5.3 下書き

- 入力中の内容はブラウザのローカルストレージに保存する。
- 画面起動時に下書きがあれば復元する。
- 手動の `下書きを復元` ボタンは表示しない。

### 5.4 PT申請

- 従業員はPT勤務日、勤務エリア、勤務店舗、開始時刻、終了時刻、備考を入力できる。
- PT申請は通常シフト希望とは別ログに保存する。
- 承認不要運用では、PT申請後に自動で確定シフトへ反映する。
- PT申請は前日まで可能とする運用を前提にする。

### 5.5 希望・確定確認

- 従業員は自分の希望シフトと確定シフトを確認できる。
- 確定シフトは `確定シフト` シートから取得する。
- 希望シフトは `シフト希望` シートから取得する。
- データ欠損があっても画面全体が落ちないように、空配列またはID表示で継続する。

### 5.6 エリア別調整

- 店長・エリア管理者はエリア確認用スプレッドシートでシフトを調整する。
- セル値で勤務時間、PT、有給、NGなどを表す。
- 背景色で通常勤務、ヘルプ勤務、調整中、休みなどを表す。
- 確定ボタン実行時、GASがセル値と背景色を読み取り、確定シフトへ変換する。

### 5.7 全体反映

- 確定ボタン実行後、全体確認用スプレッドシートの `確定シフト` を更新する。
- 全体確認用の `全体_YYYY-MM` シートを再生成する。
- エリア確認用の `エリア_エリアID_YYYY-MM` シートを再生成する。
- 変更履歴を保存する。

### 5.8 DB管理

- DB管理用スプレッドシートに、エリア、店舗、従業員、所属店舗、管理対象ファイルを持つ。
- `ID_DB` で従業員情報を編集できる。
- `ID_DBの変更を反映` メニューで従業員マスタへ反映できる。
- `管理対象ファイル` のスプレッドシートIDを変更すれば、接続先ファイルを切り替えられる。

## 6. 非機能要件

### 6.1 操作性

- スマートフォンで使いやすい2列カード型UIを基本にする。
- すべてのボタンはタップ時に押下中であることが分かる表示にする。
- 送信、クリアなど影響が大きい操作は確認画面を挟む。

### 6.2 保守性

- 店舗・従業員の増減はDB管理用スプレッドシートの編集で対応する。
- コード内に初期従業員リストや店舗リストを固定しない。
- シートとヘッダーはGASが作成し、マスタデータの中身はスプレッドシートを正とする。

### 6.3 安全性

- 通常シフト希望の受付停止は `ACCEPTING` で制御する。
- GAS側でも必須項目と入力内容を検証する。
- 確定データは見た目のシートではなく `確定シフト` を正データとする。

### 6.4 可用性

- Google Apps Script とGoogleスプレッドシートの標準稼働に依存する。
- 障害時はスプレッドシート上の保存データを確認できる状態にする。

## 7. データ要件

| データ | 保存先 |
| --- | --- |
| エリア | DB管理用 `エリアマスタ` |
| 店舗 | DB管理用 `店舗マスタ` |
| 従業員 | DB管理用 `従業員マスタ` |
| 所属/ヘルプ設定 | DB管理用 `従業員店舗設定` |
| 管理対象ファイル | DB管理用 `管理対象ファイル` |
| 希望提出 | 提出ログ用 `シフト希望` |
| PT申請 | 提出ログ用 `PT申請` |
| 確定シフト | 全体確認用 `確定シフト` |
| 変更履歴 | 全体確認用またはDB管理用 `変更履歴` |

## 8. 運用要件

- GASエディタには `Code.gs` と `GasApp.html` を貼り付ける。
- ローカル編集後はGAS側へ手動貼り替えまたは同期ツールで反映する。
- 初回は `authorizeOnce()` または `初期シート作成` を実行し、必要な権限を承認する。
- DB管理用スプレッドシートのマスタは、有効フラグで表示・非表示を制御する。
- 不要になった従業員や店舗は削除ではなく有効フラグをFALSEにする。
